# WorkBuddy 传输错误诊断

## 网络错误不等于官方 HTTP 502

WorkBuddy 请求在取得可用 HTTP 响应前发生网络异常时，报告 `provider_network_error`（网关状态 503）或可识别的 `provider_timeout`（网关状态 504）。客户端取消与请求总期限单独报告。官方实际返回 HTTP 502 时仍走原来的 HTTP 错误分支，不伪装为网络异常。

类型化信息包括白名单 `phase`、`code`、`timeoutOrigin`。可识别的连接、TLS、响应头和响应体阶段分别保留；阶段不明确时为未知，不把所有 `ECONNRESET` 都猜成连接超时。

响应体阶段已开始传输的超时/中断与“尚未收到 HTTP 响应”分开报告。状态 503/504 是网关对故障的分类，不自动代表官方返回同一 HTTP 状态。

## 不通过记录详细错误泄露凭据

只提取有界 cause / AggregateError 链中的固定原生错误码与阶段，不向客户端、账本、诊断结果复制原始异常文本、堆栈、请求 URL、头、Cookie、Token、socket 或本机地址。

未知错误保留未知。不要把缺少字段当成功，也不要从字节上界推导实际 token 数。

## 重试边界

`fetch` 失败并不证明请求体没有被上游接收。新的类型化异常不额外触发同候选重发；原有候选轮换与其它平台的既有受控策略保持。客户端取消、语义输出后的失败和结果不明都不靠盲目重放处理。

## 排查顺序

1. 用请求 ID 读取网关诊断中的候选、时刻、状态与 transport 元数据。
2. 对齐操作系统、代理/TUN和官方入口的网络记录；系统代理开关与 TUN 状态不是一回事。
3. 区分网关发起尝试、官方实际收到、完整输出、工具执行与客户端整轮完成。
4. 需要连通性检查时，无凭据小请求返回401只证明到达HTTP层，不是账号过期证据。
5. 对比当前和故障时刻；当前恢复成功不推翻历史连接失败。

配置、代理、DNS、TUN和默认模型不由错误分类逻辑自动修改。
